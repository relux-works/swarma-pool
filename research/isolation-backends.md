# Isolation backend evidence for a public execution pool

Status: Draft (2026-10-25).

Evidence cut: 2026-10-24. Mapped to the [threat model](threat-model.md); tests on representative pool machines remain unrun. This document records mechanisms, limits and open evidence; it does not select a backend.

## Scope and interpretation

The deployment under consideration runs hostile third-party builds and tests on dedicated machines with ephemeral runners and no platform secrets. These are design assumptions, not measured properties. One independently disposable sandbox or VM per trust domain is the unit evaluated here. Multiple containers in a Kata pod, or multiple jobs in a general-purpose VM, do not acquire separate VM boundaries merely by having different container names. [G01] [K01] [C02]

The adversary keys below follow the [threat model](threat-model.md) (AD-01–AD-06). The questions are bounded backend subproperties, not complete coverage of those adversaries:

| Key | Adversary | Question asked of a backend |
| --- | --- | --- |
| AD-01 | Hostile job code | Does an additional execution boundary mediate access to the runner host? |
| AD-02 | Hostile job author | Can an author-controlled image, command or configuration defeat that boundary before execution? |
| AD-03 | Neighbouring jobs, concurrent and sequential | Is isolation maintained across separate jobs and across reuse of a machine? |
| AD-04 | Compromised runner host | Can the job or platform trust execution despite control of the host? |
| AD-05 | Network adversary | Are traffic policy, confidentiality and peer authentication provided? |
| AD-06 | Platform adversarial to the job author | Can the author protect job data and establish genuine execution? |

Matrix verdicts are this document's **inferences** from the cited mechanisms, conditional on the configurations described below. `gives` asserts only the bounded property stated in that cell, under its stated configuration and trust conditions; a mechanism name alone does not establish the verdict. It is not an exploit-free guarantee or runtime qualification. `weaker, with compensation` means an external control or narrower configuration is necessary. `does not give` identifies an absent property. `unknown` means the reviewed material does not establish the property. Documentary checks cannot establish runtime security. [G01] [Q01] [F02]

Ordinary virtualization is evaluated throughout. Confidential-computing configurations, attestation services and independently verifiable computation are outside this comparison. Kata's separate confidential-computing policies do not make ordinary Kata resistant to a malicious host. A sandbox also cannot make a hostile job's claimed test result true. [K07] [KS06] [KS10] [KS13]

## Linux fact sheets

### gVisor: runsc, Sentry, Gofer and platforms

**Boundary and host requirements.** Job syscalls are implemented by the Sentry application kernel. The Sentry and Gofer still consume a restricted host Linux API; this is not merely an allowlist that forwards job syscalls. Current installation docs require Linux 5.6+ on x86-64 or arm64. Namespaces, seccomp and cgroups supply additional containment. [G01] [G12]

| Platform | Mechanism and exposed host surface | Hardware and operational limit |
| --- | --- | --- |
| systrap | Seccomp trap interception and Sentry-managed execution; host signal, memory and seccomp mechanisms remain trusted. [G02] | Supported default; no KVM required, including when the runner host is itself a VM. Actual distribution user-namespace policy still matters. [G02] [G07] |
| KVM | Sentry uses KVM for execution/address-space management; job code runs in guest userspace. This is not a conventional Linux guest with an emulated device machine. [G02] | Needs virtualization and host access to KVM. Nested operation is possible but the guide expects additional overhead; systrap often performs better there. [G02] |
| ptrace | `PTRACE_SYSEMU` interception; high context-switch cost. [G02] | Historical reference only: unsupported, expected to be removed. Existing benchmarks or GPU documentation mentioning it do not restore support status. [G02] [G06] [G10] |

**File and image path.** The Gofer's current RPC is LISAFS, not a blanket claim that current gVisor uses 9p. Directfs is enabled by default in the reviewed guide: the Gofer donates scoped mount descriptors and the Sentry performs descriptor-relative host file operations. Disabling directfs narrows the Sentry's filesystem syscall access at a performance cost. Thus “all filesystem operations go through Gofer RPC” would be inaccurate for the default. Bind mounts and image preparation remain part of the trusted setup path. [G03] [G11]

**Networking.** Default netstack terminates the guest network API in userspace, with packets reaching the host endpoint/network namespace. Host-mode networking widens exposure to the host network stack. Neither netstack nor its packet boundary implements the pool's destination policy: enforce it outside the sandbox. `network=none` removes ordinary networking but does not validate other exposed channels. [G04] [G01]

**Lifecycle and resources.** There is no full guest OS boot. Checkpoint/restore saves process state through runsc; the backing filesystem and any external dependencies must be managed consistently. The writable overlay may use memory or a host backing file. Destroying execution does not remove bind mounts' data, checkpoints, collected output or backing files. Destruction of all job-owned state is an external lifecycle contract. [G08] [G03]

Host cgroups constrain Sentry memory and threads; job memory is substantially accounted as memfd/shmem rather than host anonymous memory. Guest processes are not a one-to-one host PID population. Crucially, in-sandbox cgroup CPU/memory limits provide accounting without enforcing resource competition between processes in the same sandbox. Hard per-job isolation therefore needs a separate sandbox and complete host accounting, including helpers. [G05] [G09]

**Rootless and compatibility.** G07 explicitly distinguishes host UID from namespace UID 0 and requires the daemon/runtime/container chain to be unprivileged for its rootless definition. The built-in `--rootless` single-UID convenience path uses no external setuid binary, but lacks normal `create`, checkpoint/restore and netstack support, and ignores cgroup configuration errors. Caller-created namespaces can enable a more complete setup; multiple UID mappings require host setuid helpers such as `newuidmap`. The native rootless path also invokes mapping helpers and lacks network namespacing. These are different privilege contracts; none establishes an arbitrary rootless deployment with enforced pool limits or privilege-free host provisioning. [G07]

Language runtimes are regression-tested upstream, but kernel ABI coverage is partial. `/proc` is a virtual view, host-sensitive memory statistics differ, io_uring coverage is limited, and mounting a block filesystem or using KVM inside a sandbox is unsupported. Nested Docker has a documented path with limitations; debugger/ptrace and namespace-sensitive test tools need workload-specific verification rather than assuming Linux equivalence. [G09] [G05] [G14]

GPU support exists through nvproxy for selected devices, driver versions and ioctls. This forwards permitted NVIDIA driver operations and expands host-driver exposure; it is not a generic GPU security boundary. A GPU-enabled profile requires a separate evaluation of that expanded surface. [G10]

### Firecracker: KVM microVM and jailer

**Boundary.** Job syscalls reach a real guest Linux kernel; even compromised guest root must cross KVM and the Firecracker VMM/device boundary to reach host execution. The VMM's API socket is a privileged host control interface. The deliberately small device set includes virtio block, net and vsock; newer source also documents entropy, pmem and optional PCI transport/device-hotplug features. “No PCI ever” is outdated. Host devices, serial output, metadata service, vhost-user integrations and API options actually enabled determine the surface. [F01] [F07] [F09]

**Requirements.** Linux x86-64 or arm64, usable virtualization extensions and read/write `/dev/kvm` access are required for the VMM. The current kernel policy validates 4 KiB-page host kernels 5.10, 6.1 and 6.18; the published per-release minimums differ. This is a tested-support table, not proof that any kernel newer than a fixed minimum is supported. Nested KVM depends on the outer hypervisor exposing the CPU features and device. This document has no nested performance measurement. [F09] [F10] [N14]

**Privileges.** The jailer guide explicitly runs the jailer as host root, performs namespace/cgroup/chroot setup, then switches to the requested UID/GID before executing the VMM. It leaves the minimal capability set undetermined; do not infer a supported capability-only launch recipe. It supports cgroup v1 and v2; its documented default is v1, so unified-hierarchy deployments require explicit integration. The quickstart documents granting the VMM caller read/write KVM access or running as root, plus separate network setup. This documents component access, not an entirely unprivileged launch/stop/cleanup stack. Caller-managed jail and network cleanup must retain the necessary host authority; the reviewed material does not specify a complete non-root cleanup contract. [F03] [F10]

**Data path and controls.** File-backed block disks avoid a general host-directory sharing service in the minimal configuration. Network packets pass through a host TAP; Firecracker supplies rate limiting, not destination filtering or authenticated transport. Use a separate host policy enforcement point. Disk/network token buckets allow configured bursts; disk image capacity does not bound snapshots, serial output or logs. Production guidance explicitly discusses host-side serial/log growth and kernel worker CPU that can escape simple process-only accounting. [F01] [F02]

**Lifecycle.** Full and differential snapshot mechanisms are documented, but the reviewed source labels differential snapshots as Developer Preview. A memory/state snapshot is not a self-contained disk or network backup; feature support, CPU compatibility and guest-kernel details must be checked for the exact release. Cloning can duplicate random state, application identities, credentials and connections: VMGenID support and guest reseeding do not repair arbitrary userspace cached identity. The snapshot docs themselves have version-specific kernel/backport details; verify the guest kernel instead of assuming newer prose applies to older images. Jailer cleanup is the caller's responsibility. Kill, disk disposal, snapshot disposal, network teardown and orphan reconciliation must all complete before reuse. [F05] [F06] [F03]

**Compatibility and cost.** A guest Linux kernel supplies its own `/proc`, ptrace and container facilities when compiled/configured to do so. This improves API coverage relative to a reimplemented kernel but does not supply absent guest drivers. The minimal machine does not provide general GPU/VFIO passthrough; nested containers and nested VMs are different requirements. Published startup and memory numbers below are workload-specific, not service guarantees. [F07] [F09] [K02] [B01]

### Kata Containers: runtime, guest agent and selected VMM

**Boundary and current architecture.** A Kata sandbox/pod has a guest kernel, with the in-guest kata-agent controlled by the host shim over vsock/ttRPC. Containers in one pod share that VM boundary. The 4.x Rust architecture supports external QEMU, Cloud Hypervisor and Firecracker VMMs, plus Dragonball integrated into the shim process. Integration reduces process separation between the VMM, runtime and in-process file service; Rust alone is not an escape-prevention proof. [K01] [K02] [KS04] [KS05]

| VMM choice | Boundary-specific cost and surface | What cannot be inferred from the product name |
| --- | --- | --- |
| QEMU | Broad machine/device configuration, virtio-fs and optional device assignment; host QEMU process and helper services join the TCB. [K02] [K05] [K14] | Only a restricted machine/device set should be enabled. QEMU hardware-accelerated virtualization and TCG emulation have different security policies. [Q01] |
| Cloud Hypervisor | Rust VMM with modern virtio devices, filesystem sharing and hotplug; current upstream requires host Linux 6.8 for its supported performance/features. [H01] [K05] | Standalone upstream capability is not proof that Kata's selected integration exposes it. Guest-root containment and file-image handling have had advisories. [HS01] [HS02] |

**Files and images.** QEMU/Cloud Hypervisor commonly share container rootfs and volumes via virtio-fs; the agent mounts them in the guest. A host file daemon, its sandboxing, path-resolution rules and exported descriptors belong to the boundary. 9p is an older/alternative sharing path, not interchangeable with virtio-fs. Block-image storage and guest image handling offer different surfaces; shared writable host workspaces defeat per-job disposal. [K05] [K10]

**Host resources and networking.** Bare metal or working nested virtualization and KVM access are prerequisites for these Linux VMM configurations. Kata documents both cgroup v1 and v2. Guest CPU/memory settings and host resource limits serve different purposes. In the documented `sandbox_cgroup_only=false` model, non-vCPU processes may be placed in an unconstrained overhead cgroup. `true` is useful only with enough reserved overhead and validated placement of every applicable helper. The generated runtime configuration and actual release must be inspected. [K12] [K14]

The host network integration carries guest traffic through virtio/TAP and host policy; host networking is not simply shared with the guest. Enforce pool egress outside the guest. The host shim, vsock peer access and agent policy are separate control surfaces from IP filtering. Agent policy is configurable and generated policy must be reviewed; it is not automatic protection against a compromised host. [K06] [K03] [K07]

**Rootless and lifecycle.** The explicit runtime-rs rootless VMM contract covers QEMU variants and non-confidential Cloud Hypervisor: the shim validates host-device access, creates a per-sandbox user, and drops only the VMM privileges. The shim and virtiofsd remain host root; vhost descriptors are opened by the root shim before the drop. Host device/group/udev provisioning has separate authority. Firecracker has no rootless setting and uses its privileged jailer instead. Dragonball is outside this documented support list; that absence leaves its complete privilege contract unknown, rather than proving root is unavoidable. Lifecycle/cleanup authority beyond these components must be specified by the deployment. [K04] [F03] Startup requires a guest boot and agent readiness. Some VMMs expose snapshot primitives, but Kata's limitations document does not offer uniform runtime checkpoint/restore commands. Reuse/VM factories must not carry tenant state across trust domains. Termination does not delete snapshotter layers, host shares or outputs. [K04] [K03] [K10]

**Build/test compatibility.** A real guest kernel generally accommodates normal Linux tools, but host namespaces, device access, dynamic resource updates and kernel configuration differ by VMM. `/proc` and `/sys` mounting restrictions exist; resource enforcement may need guest, VMM and host layers. QEMU is the focused GPU option in the reviewed matrix, with additional host-driver/device-assignment exposure. Nested container support needs guest configuration; nested KVM is a separate unproven property. [K03] [K02]

## Apple-silicon fact sheets

### Virtualization.framework: Linux guests and macOS guests

**Boundary.** The framework provides hardware-backed guest execution plus configurable virtio storage, networking, sockets, entropy, graphics and sharing devices. The job uses its guest kernel, not host Darwin syscalls. Host macOS, Apple's virtualization implementation, configured virtual devices and the management application remain trusted. The public API inventory does not prove the internals have a particular process sandbox, syscall allowlist or hard host resource ceiling. [A01] [A05]

Linux guests need an appropriate arm64 image/kernel and support Linux workloads. macOS guests need the Apple platform configuration, restore image, auxiliary storage and machine identity; the current vendor sample targets macOS 27 APIs and explains adaptation for older systems. Validate each guest/host pairing rather than importing that sample's requirements as the framework's historical minimum. Native VZ does not run an x86 guest OS on arm64. Linux binary translation through Rosetta is not an x86 macOS guest. [A02] [L02] [C02]

A Linux guest cannot run Xcode, macOS frameworks or the macOS/iOS Simulator test environment. Apple lists macOS requirements for Xcode. Cross-compiling some source or running Linux Swift tools does not test Darwin APIs. A macOS guest is required for those execution checks, subject to the chosen Xcode/OS pair and guest feature support. [A09] [A02]

**Networking and sharing.** NAT gives a route to external networks; it is not a destination allowlist. Framework file-sharing devices explicitly expose host directories. The application must choose whether these devices exist and which directories, sockets, displays and services are exposed. Bridged/host-facing paths and the management application's privileges must be evaluated separately. [A06] [A07] [A05]

**Privilege evidence.** A05 describes configuration and the virtualization entitlement; A06 waives an additional networking entitlement for NAT. Neither establishes the management caller UID, helper UIDs, absence of privileged OS services, or privilege needed to stop and clean up a deployment. Both Linux-guest and macOS-guest application/helper privilege contracts remain unknown from these sources. An entitlement waiver cannot establish operation without a root daemon. [A05] [A06]

**Lifecycle and controls.** CPU count and guest RAM are configuration dimensions, not a demonstrated cap on all host helpers or IO. Save/restore exists with configuration support checks, but external disks must be handled separately. New per-job disk overlays, auxiliary storage, VM identity, saved memory and network state all need explicit ownership and deletion. Neither deleting a VM object nor unlinking its disk establishes secure erasure from storage, caches or swap. No comparable vendor start-latency benchmark or complete host CPU/memory/disk/network/PID enforcement guarantee was found in the reviewed sources. [A05] [A08] [A02]

**Nested virtualization.** The generic platform nested-virtualization API is available from macOS 15 and requires an M3-or-later Mac; probe its support property. This is not universal support on M1/M2, and not a guarantee of nesting macOS guests or of any specific Linux/KVM VMM. Avoid adding nested KVM to a job unless its workload contract requires that extra surface. [A03] [L09] [T03]

### Licensing and macOS guest limits

The reviewed **macOS Tahoe 26** SLA, section 2B(iii), conditionally permits two additional virtual copies on qualifying Apple-branded hardware already running the software, for enumerated purposes including development/testing. It does not generally authorize public multitenant hosting. Section 3's developer-service leasing route requires at least 24 hours, exclusive end-user hardware/software use, acceptance and advance notice to Apple; section 3D adds virtualization conditions. Volume or written agreements may differ. The deployed OS/license and public service model therefore require an ownership decision before admission. API capability does not enlarge license permission. [A04]

The API also defines `virtualMachineLimitExceeded`; the reviewed symbol does not specify a universal numerical limit or guarantee immediate slot reclamation after failure. The license copy allowance, OS-enforced VM quota and resource-admission limit are different constraints. Validate concurrency and slot recovery on the exact host/guest release rather than assuming two licensed copies is an API capacity guarantee. [A10] [A04]

### Lima: VZ and QEMU drivers

Lima adds host/guest agents, image downloads/conversion, SSH management, DNS, sharing and port forwarding around its VMM. Its threat model treats the guest including root as hostile, **but trusts templates and provisioning configuration** and excludes upstream VMM bugs from Lima's own scope. Therefore untrusted job authors cannot supply Lima templates directly. [L14]

[L02] | Linux guests are established; macOS guests have experimental support since 2.1 on ARM with host same/newer than guest. No automatic port forwarding for macOS guests. [L07] |

[L09] [L14] [L06]

Lima supplies configured vCPU/RAM/disk sizes, not a comprehensive host-resource accounting guarantee. Snapshot commands are experimental; separate named disks can survive instance deletion. Cold boot includes guest/agent/provisioning readiness, so wrapper lifecycle costs exceed the VMM's bare boot path. No comparable current startup or density benchmark was established here. ### Additional current options

**Tart.** Runs Linux and macOS VMs on Apple silicon using Virtualization.framework, with OCI-distributed VM images and cloning workflows. It is an automation wrapper, not a new hypervisor boundary. Its FAQ describes host NAT reachability and optional stricter networking, headless-host constraints, caches and newer copy-on-write image facilities. Registry/image parsing, credentials, control state, sharing and networking remain surfaces. The README's example downloads a 25 GB VM image; no controlled boot/RSS benchmark is established by its “near-native” performance language. FSL service restrictions need separate review. [T01] [T03] [T02] [A05]

**Apple `container` / Containerization.** Linux OCI containers each receive a lightweight VM, a small Linux guest and a vsock-managed init service. The library claims sub-second startup without a workload/hardware distribution suitable for a pool SLO. The supported Mac CLI requires macOS 26; it is not a macOS-container runtime. Its launch-agent/XPC helpers, vmnet network path, image store, registry integration and optional host shares join the TCB. Hard means enforced at the trusted host boundary for the stated resource, with a defined over-limit response. It does not mean zero transient overshoot or freedom from shared-device contention. CPU weight, memory pressure thresholds, admission reservations and advertised guest sizes alone are not equivalent to whole-job hard ceilings. [N09] [N13] [Q01]

**Illustrative arithmetic, explicitly an estimate.** For a host with 8 vCPUs and 32 GiB RAM, assume a 4 GiB host/service reserve, a 2 GiB job memory budget, 2 vCPUs per busy job, and an unmeasured 0.5 GiB overhead planning allowance per VM. Memory would admit `floor((32 - 4) / (2 + 0.5)) = 11` jobs; non-oversubscribed CPU would admit `floor(8 / 2) = 4`, hence four under these assumptions. The 0.5 GiB and 4 GiB values are planning assumptions, not vendor numbers. Storage capacity/IOPS and measured peak helpers can lower that limit; no backend has been measured against it. [N09] [K12] [Q01]

The same hypothetical 32 GiB/8-core Apple-silicon machine has the same arithmetic but no demonstrated macOS equivalent of complete Linux cgroup ceilings. macOS guest legal concurrency can bind before RAM does. Linux guest count is not subject to the cited macOS-copy clause, but hardware, guest licensing and resource controls still apply. Hardware with more unified memory does not establish isolated GPU quotas. [A04] [A05] [L10]

If the **pool host itself is a VM**, gVisor/systrap avoids a nested-hardware-virtualization dependency. Firecracker and the selected Linux Kata VMMs require exposed KVM/CPU features and a separately supported nested configuration. Nested operation adds the outer hypervisor to the trusted computing base and changes scheduling, memory accounting and latency. An outer VM's promised eight vCPUs is not eight dedicated physical cores; benchmark the actual deployment. [G02] [N14] [F10] [K12]

For Apple silicon, the M3+/macOS-15 generic nested-virtualization capability is a necessary API condition for the documented path, not proof of a supported nested macOS service or of Firecracker/Kata compatibility in that guest. With no available nested KVM, QEMU TCG is an emulation alternative for compatibility experiments, **not a replacement security boundary under QEMU's policy**. [A03] [T03] [Q01]

## Open decisions and options that survive

The unresolved decisions are tracked in [UNRESOLVED_QUESTIONS.md](../UNRESOLVED_QUESTIONS.md): backend obligations under the accepted threat model, launch-authority ownership, one-job boundary, host/nested capabilities, egress and artifact protocol, quota enforcement, image/storage lifecycle, Mac license/service model, compatibility requirements and the matched-machine test plan.

Supported gVisor platforms, Firecracker and individually constrained Kata VMM configurations remain options for Linux evaluation. Hardware-backed Apple VMs remain options for Linux-on-Mac and, subject to licensing and compatibility, macOS execution; Lima, Tart and Apple `container` supply different operational wrappers. Unsupported gVisor ptrace and QEMU TCG do not survive as current public-pool security configurations; experimental krunkit/macOS-Lima paths retain explicit evidence gaps. This is a set of options to test, not a ranking or recommendation. [G02] [F01] [K02] [Q01] [A04] [L08] [T02] [C01]
